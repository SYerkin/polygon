# Алмұрт: фронтенд-стек для mobile-first интернет-магазина

**Решение на 23 сентября 2026 года.** Цель — быстро выпустить удобный магазин с каталогом, корзиной, оформлением заказа и выразительной главной, который остаётся быстрым на обычном смартфоне. Это выбор фронтенда; платёжный провайдер, учёт товаров и система заказов требуют отдельного решения.

## Короткий ответ

**Next.js (App Router) + React + TypeScript + Tailwind CSS + Motion.** Карточки, каталог и страницы товаров рендерятся на сервере; интерактивные элементы работают в небольших клиентских компонентах. Для настоящей 3D-сцены на главной — **Three.js через React Three Fiber**, загружаемый отдельно. Для плоского персонажа из SVG — сначала **SVG + CSS/Motion**, без 3D-движка. Бэкенд магазина подключается через типизированный API.

> Самый быстрый сайт с 3D — тот, в котором магазином можно пользоваться до загрузки 3D. Товар, цена и кнопка покупки всегда доступны независимо от WebGL.

## Выбранные инструменты

| Задача | Инструмент | Как использовать |
| --- | --- | --- |
| Страницы и SEO | Next.js, App Router | Главная, категории и товары как серверные страницы; интерактивность точечно. |
| Код | TypeScript, строгий режим | Типы товаров, вариантов, корзины и ответов API. |
| Вёрстка | Tailwind CSS + CSS variables | Сначала стили для узкого экрана; фирменные цвета, шрифты, отступы и радиусы как токены. Для сложной композиции — обычный CSS module. |
| UI-анимация | Motion for React + CSS | Появления, переходы, выезжающая корзина, анимация кнопок; CSS для простых состояний. |
| 3D только на главной | Three.js + React Three Fiber; `@react-three/drei` по необходимости | Изолированный компонент `HeroScene`; динамическая загрузка после видимого контента. Формат модели — GLB/glTF. |
| Персонаж | SVG + CSS/Motion; Rive только при необходимости | Если персонаж плоский или уже собран в SVG, оживить слоями и плавными трансформациями. Rive имеет смысл, когда нужны сложные состояния, подготовленные в его редакторе. |
| Данные магазина | Существующий backend/API + типизированный клиент | Каталог, остатки, цены, промокоды и заказ приходят с сервера. Генерировать типы из OpenAPI, если спецификация есть. |
| Корзина | Локальное состояние для мгновенного отклика + проверка на сервере | На клиенте хранить позиции и количество; перед оплатой сервер повторно проверяет цены, остатки и стоимость доставки. |
| Тестирование и качество | Playwright для ключевого пути; Lighthouse и реальные Web Vitals | Проверить поиск → товар → корзина → заказ на мобильном экране. |

**Менеджер пакетов:** `pnpm`. **Деплой:** платформа с полноценной поддержкой Next.js; выбрать по доступному хостингу и инфраструктуре, а не заранее привязывать проект к одному сервису. Версии пакетов зафиксировать lockfile при старте проекта.

### Почему этот вариант

1. Серверный HTML для товара и категории помогает первому показу и индексации; клиентский JavaScript нужен лишь для интерактивных частей.
2. React Three Fiber удобно встраивает Three.js в React, но его код можно отделить от всего каталога.
3. Tailwind ускоряет адаптивную вёрстку; Motion закрывает большинство анимаций интерфейса без собственного сложного движка.
4. У тебя сильный Angular-бэкграунд: **Angular с SSR тоже рабочий выбор**, если уже есть Angular-кодовая база или команда на Angular. Для нового магазина с отдельной 3D-сценой я выбираю React/Next.js из-за связки с React Three Fiber. Смена фреймворка сама по себе не делает сайт быстрым: решают объём JS, медиа, рендеринг и API.

## Как сделать главную живой и быстрой

### Порядок загрузки

1. Сразу показывать HTML главной, меню, текст, кнопку перехода в каталог и **статичный постер** будущей сцены. Постер, если это главный крупный элемент экрана, грузить с высоким приоритетом.
2. После загрузки критического содержимого подключать анимацию персонажа и прочие некритичные эффекты.
3. Загружать `HeroScene` отдельно только на главной. Перед запуском проверять поддержку WebGL, настройку `prefers-reduced-motion` и фактическую скорость на целевых устройствах.
4. При медленной сети, слабом устройстве или ошибке WebGL оставить постер и рабочие кнопки. Если 3D находится ниже первого экрана, подключать его при приближении к области просмотра.

**Важно:** не ставить `loading="lazy"` на постер первого экрана. Не заставлять посетителя ждать загрузки GLB, чтобы увидеть название, товары или CTA. Анимации `transform`/`opacity` предпочтительнее постоянного пересчёта размеров и расположения.

### Персонаж и 3D — разные задачи

- **Маскот на главной:** начать с векторных слоёв: покачивание, моргание, лёгкий поворот, реакция на нажатие. SVG даёт чёткую графику и не требует WebGL.
- **Если нужен именно объёмный маскот:** подготовить отдельную GLB-модель с короткими анимациями; протестировать её на целевых iPhone и Android до утверждения эффекта.
- **3D-объект/сцена в hero:** одна компактная сцена, ограниченные текстуры и источники света, без тяжёлых постэффектов. Компрессию геометрии и текстур применять после проверки совместимости и времени декодирования.
- **Постоянно крутить 3D вне экрана не нужно:** останавливать рендер, когда сцена не видна; для неподвижных сцен использовать рендер по запросу. Учитывать `prefers-reduced-motion`.

## Страницы и ответственность

| Раздел | Рендеринг и поведение |
| --- | --- |
| `/` | Серверный контент + постер; маскот и 3D как отдельные клиентские островки. |
| `/catalog` и `/category/[slug]` | Серверная выдача, пагинация/фильтры в URL, изображения с правильными размерами. |
| `/product/[slug]` | Серверная карточка, наличие и цена из API; выбор варианта и «В корзину» на клиенте. |
| `/cart` | Мгновенное изменение количества; цена пересчитывается через сервер перед заказом. |
| `/checkout` | Данные заказа и платежа проверяет сервер; не хранить секретные ключи или логику итоговой цены во фронтенде. |

В проекте: `app/[locale]/...` для казахской и русской версии (`kk`, `ru`), `components/shop`, `components/hero`, `lib/api`, `lib/cart`, `styles`. Сразу предусмотреть отдельные URL языков, корректные `lang`/`hreflang`, локализованные названия и описания товаров. Для SEO — `generateMetadata`, sitemap, canonical и данные `Product`/`Offer` там, где они соответствуют фактической цене и наличию.

## Mobile-first правила интерфейса

- Начать макеты с **360–390 px**, затем проверить 320 px, 430 px, планшет и desktop; учитывать safe areas iPhone.
- Крупная зона нажатия у основных кнопок, заметная цена и наличие, короткий путь к корзине. Не прятать оформление заказа за анимацией.
- Размеры для изображений товаров задавать заранее, чтобы сетка не прыгала; первый экран оптимизировать отдельно от изображений ниже.
- На мобильном уменьшать интенсивность эффектов и количество объектов; не заменять каталог горизонтальной 3D-прокруткой.
- Языки: RU/KZ; стоимость и доставка показываются в тенге с форматированием под выбранный язык.
- Модальные окна, меню, фильтры и корзина должны работать с клавиатурой и скринридером; анимация должна уважать уменьшение движения.

## Измеримые цели перед релизом

- **Core Web Vitals в реальных мобильных данных, p75:** LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Это ориентиры качества Google, не гарантия от одного запуска Lighthouse.
- **Внутренний бюджет первой итерации:** постер hero ~150–250 КБ, отдельная 3D-модель после сжатия ориентировочно до 1–2 МБ; эти числа — стартовые ограничения проекта, которые уточняются после теста на целевых телефонах и сети.
- Проверить главную **с 3D и без неё** на среднем Android, Safari iPhone и медленной мобильной сети. Кнопки, каталог и оформление заказа обязаны работать в обоих режимах.
- Отдельно замерить размер клиентского JS на страницах товара и каталога: зависимости Three.js не должны попадать в их начальный код.

## Порядок разработки

1. Дизайн-токены, шрифты, мобильная сетка, шапка и навигация.
2. Каталог, карточка товара, корзина и оформление заказа с настоящим API или чётким контрактом API.
3. SEO и локализация RU/KZ; изображения товаров и метаданные.
4. Статичная главная с постером и лёгкой анимацией SVG-персонажа.
5. Изолированный прототип 3D-сцены; включить в продакшен только после замеров на мобильных.
6. Проверка покупки, доступности, ошибок API и реальных Web Vitals.

## Что нужно определить до подключения магазина

Поставщик каталога и заказов; наличие и варианты товаров; правила доставки; платёжный провайдер в Казахстане; нужна ли админка; требования к авторизации; редактирование контента главной. Эти решения меняют интеграцию и checkout, но не мешают начать вёрстку и разработку каталога по согласованному API-контракту.
